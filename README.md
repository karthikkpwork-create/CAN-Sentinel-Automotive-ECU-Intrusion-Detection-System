# CAN-Sentinel

CAN-Sentinel is an educational automotive CAN monitoring and intrusion-detection project. It combines synthetic CAN traffic generation, labeled attack datasets, rule-based monitoring, an Isolation Forest anomaly detector, and a PyQt dashboard.

All ECU names, CAN identifiers, payload layouts, and traffic patterns are invented for this project. CAN-Sentinel is a lab-only system and must not be used to connect to or test a real vehicle.

## Project goals

- Generate reproducible benign and attack CAN traffic without hardware.
- Capture and compare sender and independently observed virtual-bus traffic.
- Provide labeled datasets for injection, unknown-ID, payload-tampering, missing-message, mixed, and normal scenarios.
- Detect anomalous traffic with heuristics and machine learning.
- Present frames and alerts in a desktop dashboard.
- Keep the workflow understandable and suitable for testing and demonstration.

## Implemented components

| Component | Implementation status |
|---|---|
| Normal synthetic traffic simulator | Implemented; supports hardware-free dry-run mode |
| Synthetic attack simulator | Implemented; supports injection, unknown ID, payload tampering, missing message, mixed traffic, and normal baseline |
| Labeled dataset generator | Implemented; writes traffic, suppressed frames, event metadata, and attack windows |
| CAN monitor | Implemented in Python for Linux SocketCAN |
| Sender/observer comparison | Implemented for independent verification of transmitted and observed frames |
| PyQt dashboard | Implemented; supports CSV playback, live virtual-bus bridging, frame inspection, charts, filters, and alerts |
| Rule-based dashboard detector | Implemented; uses a learned baseline and heuristic checks |
| Window feature extractor | Implemented; extracts one-second traffic features |
| Offline Isolation Forest pipeline | Implemented and evaluated on synthetic datasets |
| Live ML inference | Not implemented |

## Architecture

```text
Configuration
  config/config.example.json
           |
           v
Normal / attack simulator --> CSV capture or Linux vcan0
                                     |
                                     v
                            Feature extractor
                                     |
                                     v
                         Rule detector or Isolation Forest
                                     |
                                     v
                         Alerts and frame dashboard
```

The sender log describes frames generated by the simulator. The observed dataset is written by a separate CAN monitor process. They are deliberately kept separate so the project can verify what was sent and what was actually observed.

## Requirements

- Python 3.10 or newer is recommended.
- Simulator and dry-run dataset generation use the Python standard library.
- Machine-learning features require pandas, NumPy, scikit-learn, and joblib.
- The desktop dashboard requires PyQt5 and pyqtgraph.
- Live capture and virtual CAN require Linux or WSL with SocketCAN and `python-can`.

## Installation

Create a virtual environment from the repository root:

```bash
python -m venv .venv
```

Activate it on Linux or WSL:

```bash
source .venv/bin/activate
```

Activate it on Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

Install the dashboard dependencies:

```bash
python -m pip install -r dashboard/requirements.txt
```

Install the offline detector dependencies:

```bash
python -m pip install -r requirements-detector.txt
```

For the separate feature-CSV model pipeline, install the pinned ML versions:

```bash
python -m pip install -r requirements.txt
```

On Linux or WSL, install `python-can` for live bridge and SocketCAN use:

```bash
python -m pip install python-can
```

## Safe offline demo

Dry-run mode does not open a CAN interface and does not transmit anything.

Generate synthetic normal traffic:

```bash
python -m src.simulator.normal_traffic_simulator \
  --config config/config.example.json \
  --dry-run --duration 3 --seed 42 \
  --output data/generated/dashboard_demo.csv
```

Open the capture in the dashboard:

```bash
python dashboard/dashboard.py data/generated/dashboard_demo.csv
```

Open the lightweight frame table instead:

```bash
python dashboard/frame_table.py data/generated/dashboard_demo.csv
```

The repository also includes a reproducible sample at [`data/samples/sample_attack_dry_run_seed42.csv`](data/samples/sample_attack_dry_run_seed42.csv).

## Generate attack datasets

Create normal, injection, unknown-ID, payload-tampering, missing-message, and mixed datasets without sending frames:

```bash
python scripts/generate_datasets.py \
  --config config/config.example.json \
  --duration 60 --seed 42 \
  --output-dir data/generated/demo
```

The generator also writes:

- `attack_windows.csv` with ground-truth attack time ranges.
- `.events.json` metadata for each scenario.
- separate suppressed-frame CSVs for missing-message and mixed scenarios.

Generate one scenario directly:

```bash
python -m src.simulator.attack_traffic_simulator \
  --config config/config.example.json \
  --dry-run --attack mixed --duration 30 --seed 42 \
  --output data/generated/mixed_traffic.csv
```

Supported attack modes are `none`, `injection`, `unknown_id`, `payload_tampering`, `missing_message`, and `mixed`.

## Offline ML pipeline

### Dashboard-oriented raw-CSV detector

Train an Isolation Forest bundle from normal raw CAN traffic:

```bash
python -m src.detector.detector train \
  --normal-csv data/generated/normal_traffic.csv \
  --model models/detector.joblib \
  --seed 42
```

Detect anomalous windows in a labeled or unlabeled raw CAN CSV:

```bash
python -m src.detector.detector detect \
  --csv data/generated/mixed_traffic.csv \
  --model models/detector.joblib \
  --check-labels
```

This interface extracts window features internally. It can report the suspect CAN ID and reason for an anomalous window.

### Automated offline demo

The Bash demo script trains and tests a temporary detector on separate generated datasets:

```bash
bash scripts/run_pipeline_demo.sh offline --duration 60 --seed 42
```

Keep the temporary datasets and model for inspection:

```bash
bash scripts/run_pipeline_demo.sh offline --duration 60 --seed 42 --keep
```

The script does not touch the real CAN interface or write into `models/` unless `--model` is supplied.

### Feature-CSV model pipeline

Extract fixed time-window features:

```bash
python -m src.ml.extract_features \
  data/generated/normal_traffic.csv \
  --output data/features/normal_traffic_features.csv \
  --window-seconds 1
```

Train and evaluate the checked-in feature-CSV workflow:

```bash
python src/ml/train_detector.py \
  --train data/features/normal_train_features.csv \
  --validation data/features/normal_validation_features.csv \
  --test data/features/mixed_traffic_features.csv \
  --output-dir models
```

Run prediction against a feature CSV:

```bash
python src/ml/predict.py \
  --input data/features/mixed_traffic_features.csv \
  --model-dir models \
  --output reports/predictions.csv
```

The raw-CSV detector and feature-CSV model are separate implementations and should not be assumed to use interchangeable model files.

## Current Isolation Forest model

The checked-in feature-CSV model uses five inputs:

- `frames_per_second`
- `unique_id_count`
- `iat_mean`
- `iat_std`
- `payload_change_rate`

Training and threshold settings:

| Setting | Value |
|---|---:|
| Algorithm | Isolation Forest |
| Estimators | 200 |
| Random state | 42 |
| Training windows | 40 |
| Validation windows | 20 |
| Threshold quantile | 95th percentile |
| Current threshold | 0.5094646190632834 |

An anomaly score above the threshold is classified as `ANOMALY`; otherwise it is `NORMAL`.

The scenario evaluation produced:

| Scenario | Precision | Recall | F1-score | False-positive rate |
|---|---:|---:|---:|---:|
| Injection | 57.69% | 100.00% | 73.17% | 24.44% |
| Missing message | 55.56% | 100.00% | 71.43% | 26.67% |
| Payload tampering | 31.25% | 33.33% | 32.26% | 24.44% |
| Unknown CAN ID | 57.69% | 100.00% | 73.17% | 24.44% |
| Mixed traffic | 84.38% | 81.82% | 83.08% | 18.52% |

These results are based only on simulator-generated data. Payload tampering is weak, and false-positive rates remain significant. See [`docs/ml_model.md`](docs/ml_model.md) and [`docs/ml_design.md`](docs/ml_design.md).

## Dashboard

Run the main dashboard:

```bash
python dashboard/dashboard.py
```

Main controls and features include:

- Opening saved frame CSV files.
- Filtering traffic by CAN ID.
- Viewing frame details and payload bytes.
- Frame, alert, and per-ID counters.
- Message-rate and busiest-ID charts.
- Loading alert CSVs.
- Exporting live captures to CSV.
- Toggling dark and light themes.
- Cycling the rule detector through off, learning, and active states.

Live rule-based alerts are disabled by default. To enable them, start live mode, click **Detector: Off** once to begin learning, send at least 12 seconds of normal traffic, then click **Learning...** again and verify the button says **Detector: On** before starting an attack.

The **Add test alert** action creates four UI-only demonstration alerts (injection, unknown ID, payload tampering, and missing message), each with a different CAN ID. It does not invoke the detector.

See [`dashboard/README.md`](dashboard/README.md) for dashboard-specific details.

## Live virtual CAN mode

Live mode is intended for Linux or WSL. Do not run it against a real vehicle bus.

Create and enable a virtual interface:

```bash
sudo modprobe vcan
sudo ip link add dev vcan0 type vcan
sudo ip link set up dev vcan0
```

Start the CAN monitor in one terminal:

```bash
python -m src.capture.can_monitor \
  --config config/config.example.json \
  --save --duration 10
```

Send benign synthetic traffic in another terminal:

```bash
python -m src.simulator.normal_traffic_simulator \
  --config config/config.example.json \
  --interface vcan0 --duration 10
```

For the desktop dashboard live bridge, start the bridge:

```bash
python dashboard/vcan_bridge.py
```

Then start the dashboard and press **Start live**:

```bash
python dashboard/dashboard.py
```

The bridge listens on TCP port `8765` and the dashboard connects to `127.0.0.1:8765` by default. The bridge binds to all network interfaces, so it should only run in a trusted lab network with restricted access.

### Generate different live alert types

With the bridge running and the dashboard connected to `vcan0`, learn a normal baseline first:

1. Click **Detector: Off** in the dashboard.
2. Run normal traffic for at least 12 seconds:

   ```bash
   python3 -u -m src.simulator.normal_traffic_simulator \
     --config config/config.example.json \
     --interface vcan0 --duration 12 --seed 42
   ```

3. Click **Learning...** again and confirm that the button changes to **Detector: On**.
4. Run one attack scenario at a time from the repository root:

   ```bash
   python3 -u -m src.simulator.attack_traffic_simulator --config config/config.example.json --interface vcan0 --attack injection --duration 40 --attack-start 15 --attack-duration 20 --seed 42
   python3 -u -m src.simulator.attack_traffic_simulator --config config/config.example.json --interface vcan0 --attack unknown_id --duration 40 --attack-start 15 --attack-duration 20 --seed 42
   python3 -u -m src.simulator.attack_traffic_simulator --config config/config.example.json --interface vcan0 --attack payload_tampering --duration 40 --attack-start 15 --attack-duration 20 --seed 42
   python3 -u -m src.simulator.attack_traffic_simulator --config config/config.example.json --interface vcan0 --attack missing_message --duration 40 --attack-start 15 --attack-duration 20 --seed 42
   ```

   Or run the scheduled mixed scenario:

   ```bash
   python3 -u -m src.simulator.attack_traffic_simulator \
     --config config/config.example.json \
     --interface vcan0 --attack mixed --duration 120 --seed 42
   ```

The simulator sends CAN frames, not alert labels. The dashboard infers suspicious behavior with heuristic rules, so an attack scenario may produce a different alert type or no alert. The bridge's `interval anomaly` alerts are separate from the dashboard detector's rule-based alerts. Use these commands only with the virtual `vcan0` interface, never a real vehicle bus.

## Rule-based detector

`dashboard/detector.py` is separate from the Isolation Forest models. It can:

- Learn a baseline from observed frames.
- Detect unfamiliar CAN IDs.
- Flag unusually fast frames.
- Detect unexpected payload or DLC changes.
- Detect missing messages.

Its thresholds are heuristic assumptions rather than validated production settings. Alert cooldown prevents repeated reports for the same condition.

## Limitations

- The evaluation uses synthetic datasets, not independent real-vehicle captures.
- The model may have significant false positives.
- Payload-tampering detection needs better features and validation.
- Unknown-ID detection should use a learned or configured allowed-ID list.
- Missing-message detection should use expected ECU schedules.
- Live ML inference and end-to-end detection latency on `vcan0` are not implemented.
- Live virtual-CAN operation is not a claim of real automotive safety or security certification.
- CAN arbitration IDs do not reveal the physical ECU sender; the dashboard reports CAN IDs and message names, not guaranteed ECU identities.

## Safety and responsible use

Use synthetic traffic and virtual CAN interfaces only. Keep the project isolated from real vehicles, production networks, and safety-critical systems. Never infer that an anomaly proves a cyberattack, and do not use this project as a sole security control.
